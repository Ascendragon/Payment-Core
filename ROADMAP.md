## Часть I. Обзор проекта

### 1.1 Что это
Money-transfer ядро на **Symfony 8 / PHP 8.4 / PostgreSQL / RabbitMQ / Redis**.
Единственный бизнес-эндпоинт — `POST /api/transfer` (перевод между счетами с
идемпотентностью). Write-путь построен на **сыром Doctrine DBAL** (не ORM).

### 1.2 Карта архитектуры (как есть на 2026-06-06)
```
HTTP POST /api/transfer
  → TransferController
       ├── #[MapRequestPayload] TransferRequest  (валидация: NotBlank/Uuid/Regex)
       ├── вручную читает заголовок Idempotency-Key (нет ключа → инлайн 400, баг NEW-6)
       └── TransferService::transfer(...)                  ← нет типа возврата (NEW-3)
              ├── IdempotencyKey::fromHeader()  (VO, длина ≤ 64)
              ├── requestHash = sha256(from+to+amount+currency)
              ├── new Money($amount, $currency)            ← минуя ::of() (C2 → NEW-1)
              ├── store->acquire(...)        ← ВНЕ транзакции (C3); FOR UPDATE no-op (NEW-5)
              └── retryRunner->run(closure):               ← своя транзакция + ретраи
                     load sender/receiver (SELECT)
                     проверки валюты / средств (Money)
                     UPDATE sender   (optimistic lock: version = version+1 WHERE version=:v)
                     UPDATE receiver  (CAST VARCHAR↔NUMERIC, C1; минуя Money, NEW-7)
                     outboxStore->save(TransferCompletedMessage)
                     store->markAsCompleted()              // ревизия: ВНУТРИ транзакции — ок

OutboxProcessCommand (one-shot, LIMIT 50, без SKIP LOCKED/ORDER BY, статусы-строки, A5)
  → MessageBrokerInterface (RabbitMQ через Messenger)
  → TransferCompletedHandler

Ошибки: ApiExceptionSubscriber (kernel.exception) → {error:{code,message}}  // ревизия: переписан, чисто
```
Слои: `Domain/` (VO `Money`, `IdempotencyKey`; enum-ы статусов; исключения;
message) · `Application/` (`TransferService`) · `Infrastructure/` (Dbal-сторы,
retry, брокер, метрики) · `Contracts/` (порты) · `Controller/` · `Http/Request/`
(DTO) · `EventSubscriber/` (маппинг ошибок в HTTP) · `Entity/`+`Repository/`
(ORM — фактически только источник схемы, см. 1.4).

### 1.3 Сильные стороны (это уже хорошо — не сломай при рефакторинге)
- **Идемпотентность** через `INSERT ... ON CONFLICT DO NOTHING` + статус + хэш
  запроса (защита от подмены тела под тем же ключом).
- **Оптимистичная блокировка** (`version = version + 1 WHERE version = :v`) + ретраи
  на `ConcurrencyConflictException` с backoff.
- **Transactional Outbox** — событие пишется в одной транзакции со списанием
  (атомарность «изменили деньги ⇔ записали факт»).
- Чёткое **разделение на слои** и порты (`Contracts/`).
- **Money — Value Object на bcmath**: деньги не считаются во float; есть
  `of()`/`subtract()`/`isGreaterOrEqual()` с проверкой валюты.
- **Централизованный маппинг исключений** в HTTP (`ApiExceptionSubscriber`,
  формат `{error:{code,message}}`, логирование только 5xx). // ревизия: сделано чисто
- **Богатая таксономия доменных исключений** (`Domain/Transfer/Exception/*`) —
  каждый отказ имеет своё имя и свой HTTP-код. // ревизия: новое, хорошо
- **enum-ы статусов** (`IdempotencyStatus`, `PaymentStatus`) вместо магических
  строк в части кода. // ревизия: новое
- **Валидация на DTO** через атрибуты (`TransferRequest`) + автогенерация OpenAPI.
- Есть **интеграционные тесты** на ключевые сценарии (5 шт.).

### 1.4 Главное архитектурное противоречие + N1 (доказано по миграциям)
Сосуществуют **две несовместимые модели данных**: ORM-сущности (`Account`, `Payment`…)
с геттерами/сеттерами — и **сырой DBAL/SQL** в сервисе, который их игнорирует. На
write-пути сущности мертвы как поведение, но **живы как источник схемы** — и именно
через них схема деградировала.

**N1 — механизм регрессии (центральный урок проекта).** Миграция 1
(`Version20260221144322`, рукописный DDL) задавала **правильную** схему:
`balance numeric(18,2) CHECK (balance>=0)`, `amount numeric(18,2) CHECK (amount>0)`,
UUID-id, FK между payments/accounts/idempotency, `UNIQUE (account_id, key)`, JSONB+индексы.
Затем кто-то выполнил `make:migration` — Doctrine сравнила БД с **анемичными сущностями**
и сгенерировала миграцию 2 (`Version20260307002900`), которая **снесла хорошую схему**:
`balance VARCHAR(255)` (CHECK исчез), `payment.amount VARCHAR(25)` + `id INT` вместо UUID
(CHECK и UUID исчезли), `UNIQUE (key)` вместо `(account_id,key)` (отсюда NEW-4), JSONB→JSON.
`down()` миграции 2 буквально восстанавливает хорошую схему — то есть это **чистая деградация**.
> **Урок senior-уровня:** ORM-маппинг — это авторитет над схемой. Анемичные сущности →
> `make:migration` *верно* деградирует БД под них: CHECK, NUMERIC, FK, составной UNIQUE —
> всё, что ORM «не видит», молча удаляется. `Account` это подтверждает: `id` — `?string`
> с `getId(): ?int` при `VARCHAR(255)` в БД; `balance` — `#[ORM\Column(length:255)]`,
> у сущности **нет понятия** numeric/scale/CHECK≥0.

Это надо осознанно разрешить (шаг 1.0): либо сущности **выражают** инварианты (Вариант А),
либо авторитет над схемой забираем у ORM в рукописные миграции (Вариант Б — частый выбор
в финтехе именно поэтому). Решение политическое (ownership), не техническое.

### 🔴 Корректность / целостность данных
- **C1.** Баланс хранится как `VARCHAR(255)` (миграция 2). Апдейт получателя — через
  `CAST(... AS NUMERIC)` туда-обратно. Нужно `NUMERIC(20,2)` + `CHECK (balance>=0)`.
- **C2.** Инвариант `Money` обходится: конструктор **public**, в сервисе деньги
  создаются `new Money(...)` (строки 46, 73) минуя `Money::of()`. Нет `add()`,
  scale жёстко = 2 (для JPY = 0 знаков — сломается). Покрыть юнит-тестами.
- **C3.** `acquire()` идемпотентности вызывается **вне** транзакции перевода.
  При откате (`InsufficientFunds` и пр.) строка остаётся в статусе `Processing`
  навсегда → «отравленный ключ», все повторы вечно ловят 409 `AlreadyProcessing`.
  Метод `markAsFailed()` не реализован (enum `IdempotencyStatus::Failed` уже есть).
- **NEW-1. Перевод на 0 проходит.** Регэксп суммы `^\d+(\.\d{1,2})?$` пропускает
  `0` и `0.00`. `Money::of()` это отбил бы (`> 0`), но в сервисе `new Money()`,
  поэтому нулевой перевод исполняется: баланс не меняется, но `version++` и
  событие в outbox улетает. Это конкретное последствие C2 — лечится тем же шагом.

### 🟠 Архитектура
- **A1.** `TransferService::transfer()` — транзакционный скрипт ~90 строк, всё в
  одном замыкании. Тестируется только интеграционно (нужна БД).
- **A2.** Анемичная доменная модель: `Account`/`Payment` — только геттеры/сеттеры,
  бизнес-правила живут в SQL внутри сервиса, а не в агрегате.
- **A3.** `MetricsCollectorInterface` + `RedisMetricsCollector` написаны, но **не
  подключены** к сервису (нет ни одного вызова).
- **A4.** `Payment`/`PaymentStatus`/`AuditLog` — таблицы есть, записей нет.
  Нет источника истины по платежам; `idempotency_key.payment_id` всегда NULL.
- **A5.** Outbox-relay небезопасен: `OutboxProcessCommand` без
  `FOR UPDATE SKIP LOCKED`, без `ORDER BY` (нет FIFO), one-shot вместо воркера,
  статусы — строковые литералы (`'Pending'`/`'Sent'`), нет обработки ошибки
  dispatch и backoff. Два воркера = дубликаты отправки.
- **NEW-2. Мёртвая зависимость.** В `TransferService` инжектится
  `MessageBrokerInterface $messageBroker`, но он **нигде не используется** (всё
  идёт через outbox). Лишняя связь — убрать из конструктора.
- **NEW-4. Сменилась семантика идемпотентности.** В хорошей схеме был
  `UNIQUE (account_id, key)` — ключ уникален **в рамках счёта**. В живой схеме
  индекс `idx_unique_key` стоит на **`key` одном** — ключ стал **глобальным**.
  При этом `acquire`/`markAsCompleted` всё ещё фильтруют по `account_id AND key`.
  Это рассогласование «как задумано / как в БД» — и хороший вопрос на архитектуру:
  идемпотентность должна быть глобальной или по счёту/клиенту?
- **NEW-6. Два формата ошибок + размазанная ответственность.** Отсутствие
  заголовка `Idempotency-Key` обрабатывается **в контроллере** инлайном и отдаёт
  `{error:"строка"}` со статусом 400, тогда как всё остальное идёт через
  `ApiExceptionSubscriber` и отдаёт `{error:{code,message}}`. Контракт API
  неконсистентен; проверка ключа должна жить там же, где остальные ошибки.
- **NEW-7. Получатель апдейтится мимо `Money`.** Отправитель считается через VO
  (`subtract`), а получателю прибавляется сырой `:amount` прямо в SQL c CAST.
  Асимметрия: получатель не проходит проверку валюты/scale через VO.
- **NEW-9. Непоследовательная стратегия исключений.** Таксономия доменных исключений
  есть, но сервис её обходит: `same-account` (стр. 37) и **несовпадение валюты**
  (стр. 66/70) кидают голый `\InvalidArgumentException`, хотя `Money` для того же концепта
  кидает `CurrencyMismatchException`. Один концепт = два разных HTTP-ответа. Привести к таксономии.
- **NEW-10. У `Money` нет `add()`** — поэтому получателю и приходится прибавлять сумму
  сырым SQL с CAST (корень NEW-7). Мелочь на стыке: `acquire()` передаёт `account_id`
  как объект `Uuid`, а `markAsCompleted()` — строкой (`toRfc4122()`). Разнобой типов на границе DBAL.

### Фаза 1 — Схема, деньги и идемпотентность (целостность данных)
> Концепция: инвариант должен быть **невозможен к нарушению** на уровне БД и типов,
> а не «проверен вручную». Сначала чиним фундамент данных, потом строим на нём.

- `[ ]` **1.0 Разрешить регрессию схемы (N1) — развилка.** Реши осознанно, кто
  источник истины по схеме:
  - **Вариант А (рекомендую для обучения):** ORM-сущности — источник схемы.
    Чиним `Account` (UUID-id, `balance` numeric, `version`, timestamps),
    `Payment` (UUID-id, numeric amount, enum-статус, FK), затем `make:migration`
    генерирует чистую миграцию.
  - **Вариант Б:** отказаться от ORM как источника схемы, держать DDL в рукописных
    миграциях, сущности — только для read-моделей (или удалить).
  *Приёмка:* свежая БД с нуля (`migrate`) даёт схему с `numeric`, FK и CHECK;
  «хорошая» схема не откатывается второй миграцией. *Подумать:* кто в платёжной
  системе должен владеть схемой — ORM-маппинг или рукописные миграции? Почему
  в финтехе это чаще миграции?
- `[ ]` **1.1 Баланс → деньги.** `account.balance` → `NUMERIC(20,2)` +
  `CHECK (balance >= 0)`; убрать `CAST` в апдейте получателя (просто
  `balance = balance + :amount`, NEW-7). Поправить тесты, где баланс сравнивается
  со строкой без дроби (`'130'` → `'130.00'`).
- `[ ]` **1.2 `Money` — закрытый инвариант.** Приватный конструктор + только
  `Money::of()`; `new Money(...)` из сервиса убрать (лечит C2 и NEW-1 — нулевой
  перевод); добавить `add()`, сравнения; scale в зависимости от валюты. Покрыть
  юнит-тестами (включая кейс «0 и отрицательное — отказ», «JPY без дробной части»).
- `[ ]` **1.3 Идемпотентность в одной транзакционной границе.** `acquire` либо
  внутри той же транзакции, что и перевод, либо с компенсацией: поймать исключение
  вокруг `run`, в отдельной короткой транзакции выставить `markAsFailed()` (лечит
  C3). Заодно реши NEW-4: оставляем глобальный ключ или возвращаем `(account_id,key)`.
  *Подумать:* `FOR UPDATE` в `acquire` сейчас в autocommit и не блокирует ничего
  (NEW-5) — нужен ли он вообще при `INSERT ON CONFLICT`?
- `[ ]` **1.4 Тесты целостности.** «Упавший перевод (`InsufficientFunds`) не
  оставляет ключ в `Processing` и повтор проходит, а не ловит вечный 409»;
  «нулевой/отрицательный перевод отбивается».
  *Приёмка фазы:* нельзя создать нулевые/отрицательные деньги; баланс — числовой
  тип в БД с CHECK; повтор после сбоя работает.

### Фаза 2 — Богатая доменная модель (самый ценный шаг для Senior)
> Концепции: Aggregate, Domain Events, Tell-Don't-Ask, Ports & Adapters (Hexagonal).
> Здесь ты перестаёшь «писать SQL в сервисе» и начинаешь моделировать предметную область.

- `[ ]` **2.1 `Account` — настоящий агрегат.** `withdraw(Money)` / `deposit(Money)`
  с проверкой инвариантов и инкрементом `version` внутри; геттеры/сеттеры убрать;
  баланс — `Money`, не строка.
- `[ ]` **2.2 Порт `AccountRepository`** в `Domain`, реализация на DBAL в
  `Infrastructure` (load с версией, save с optimistic-lock). Сервис зависит от
  порта, не от `Connection`.
- `[ ]` **2.3 Ужать `TransferService` до оркестрации:** `load → withdraw → deposit
  → save → record event`. Событие `TransferCompleted` поднимать **из агрегата**.
  Убрать мёртвый `messageBroker` (NEW-2) и проставить тип возврата (NEW-3).
- `[ ]` **2.4 Записывать `Payment`** (источник истины по факту перевода),
  заполнять `idempotency_key.payment_id` (A4).
  *Приёмка:* `TransferService` < 40 строк; бизнес-правила покрыты юнит-тестами
  **без БД**; `ConcurrencyConflict` по-прежнему ретраится.

### Фаза 3 — Надёжность доставки и наблюдаемость
> Концепции: at-least-once delivery, идемпотентные консьюмеры, метрики/логи/трейс.

- `[ ]` **3.1 Безопасный outbox-relay (A5):** `SELECT ... ORDER BY created_at
  FOR UPDATE SKIP LOCKED LIMIT N`, статусы-enum, обработка ошибки dispatch с
  backoff/retry-count, воркер (loop) вместо one-shot. *Подумать:* почему outbox
  даёт at-least-once, а не exactly-once, и где тогда нужна идемпотентность консьюмера?
- `[ ]` **3.2 Подключить `MetricsCollector` (A3):** success/fail, retry-count,
  длительность перевода.
- `[ ]` **3.3 Логи и корреляция:** `error_log`/прочее → `LoggerInterface`;
  correlation-id сквозь HTTP-запрос → outbox-сообщение → консьюмер; время через
  `Clock` (NEW-8).
  *Приёмка:* два параллельных relay-воркера **не дублируют** отправку (тест).

### Фаза 4 — Тестовая пирамида
> Концепция: юнит / интеграция / конкурентность — это **разные виды уверенности**,
> а не «много тестов». Дешёвые и быстрые — внизу, дорогие и медленные — вверху.

## Часть V. Трейд-оффы по стеку и ключевым решениям
> Для роста в архитектора важнее уметь **объяснить, почему так**, чем знать «как
> правильно». Ниже — решения, заложенные в проекте, и их компромиссы.

- **Сырой DBAL vs ORM на write-пути.** Сейчас write — сырой SQL. Плюсы: полный
  контроль над `UPDATE ... WHERE version=:v`, предсказуемый план, нет «магии»
  identity-map/flush. Минусы: бизнес-правила утекают в SQL (A2), нет переносимости,
  ручной маппинг. Типичный зрелый выбор в финтехе: **домен богатый, репозиторий
  на DBAL** (контроль), ORM — для read-моделей/админки. Это шаги 2.1–2.2.
- **PostgreSQL.** `NUMERIC` для денег (точность), транзакции, `FOR UPDATE SKIP
  LOCKED` для очередей/outbox, `ON CONFLICT` для идемпотентности. Альтернатива —
  считать деньги в minor units (целые копейки) `BIGINT`: быстрее и без `NUMERIC`,
  но переполнение и валюты с 3 знаками усложняют. Обсуждается в 1.1/5.1.
- **Оптимистичная блокировка (version) vs пессимистичная (SELECT FOR UPDATE).**
  Оптимистичная: дёшево при низкой конкуренции на один счёт, но нужны ретраи
  (есть). Пессимистичная: проще рассуждать при «горячих» счетах, но риск
  deadlock/контеншена. Вопрос на 4.2: какой профиль нагрузки у твоих счетов?
- **Transactional Outbox vs прямой dispatch / Messenger doctrine-transport.**
  Outbox даёт атомарность «деньги ⇔ событие» и **at-least-once**, ценой
  отдельного relay и дедупликации у консьюмера. Альтернатива — Messenger с
  doctrine-транспортом (тот же принцип «через БД»), меньше своего кода, но меньше
  контроля над схемой/мониторингом. Шаг 3.1.
- **Идемпотентность: глобальный ключ vs (account_id, key) vs (client_id, key).**
  Сейчас рассогласовано (NEW-4). Глобальный проще, но один клиент может «занять»
  чужой ключ. Per-client — отраслевой стандарт (Stripe). Решение в 1.3.
- **RabbitMQ + Redis.** Брокер — асинхронная доставка событий; Redis — метрики
  (A3, пока не подключены). Трейд-офф Redis-метрик: дёшево и быстро, но это не
  Prometheus (нет гистограмм/скрейпинга из коробки) — отсюда «временная»
  реализация `observeTransferDuration`. Обсуждается в 3.2.
